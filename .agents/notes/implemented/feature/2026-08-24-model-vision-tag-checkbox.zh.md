# Agent Note：模型设置页的手动视觉能力标记

Status: implemented

[English](2026-08-24-model-vision-tag-checkbox.md) | 中文

## 问题

模型是否接受图片输入此前完全在产品之外决定：安装目录自带的 pi-ai 路由继承每个条目的 `input` 声明，而手工声明的网关路由回退到其 `defaultInput`（默认仅文本）。在这类路由上列出视觉模型的部署——`deepseek-v4-flash-vision-exp`、`mimo-v2-omni`、qwen 等——全部被归类为纯文本，附加图片时即使端点本身接受图片也会以「模型不支持图片」失败。唯一的修复办法是手动编辑 `settings.yaml` 加上 `input: ['text', 'image']`。

## 决策

Models 设置页的两个模型编辑器都在显示名称旁增加每行的「视觉」复选框。复选框读写该行显式的模态声明——pi-ai 行写 `input`，DeepSeek 目录行写 `inputModalities`；两个状态都固定该字段（勾选写 `['text', 'image']`，取消勾选写 `['text']`），因为在目录路由上缺失字段会继承安装条目的声明，而「未勾选」必须意味着仅文本，而不是「目录说什么就是什么」。未触碰的行继续继承。

能力数据存在的地方自动流动，无需重填：基于目录的发现现在把每个安装条目的模态作为 `LlmDiscoveredModel` 的 `inputModalities` 返回（穿过 `LlmRuntime.discoverModels` 的重建和 `llm.discoverModels` 线协议视图），采纳候选时用应答方的声明填充该行。列表端点不披露模态，网络发现的行保持路由默认。没有添加任何按名称猜测的启发式；识别仍然只有两个来源——安装目录和显式声明。

## 已考虑的替代方案

- **从模型名猜测模态**（`vision`、`omni` 子串）：硬编码的虚构，遇到命名不同的网关立即失准。
- **保存时向端点探测一张图片**：消耗 token，要求配置时就有可用密钥，且无法区分网关级拒绝与模型级拒绝。
- **复选框展示继承后的有效状态**：需要设置页并不具备的逐提供方有效模型查询；改为在提示文字中说明继承规则。
- **只做路由级 defaultInput 编辑器**：一个开关服务所有模型，无法表达网关同时服务视觉与纯文本模型的常见情况。

## 后果

用户对一行从未编辑过的行取消勾选「视觉」，会把整个用户持有的模型数组物化出来，并把该行固定为纯文本——与其他行编辑已有的覆盖语义相同。未被采纳或编辑过的目录视觉行,其复选框显示为未勾选；提示文字点明这一点而非掩盖。发现采纳现在信任应答方的声明，过度声明的目录会把错误传播下去，直到用户把该行固定住——这与请求时门控对声明给予的信任相同。
