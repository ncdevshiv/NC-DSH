# Agent Note: 拒绝对外部增长的 JSONL 日志追加

Status: implemented

[English](2026-08-23-jsonl-single-writer-append-guard.md) | 中文

## 问题

JSONL 后端只对照所属协调器的内存游标检查追加连续性，而冷恢复提交的 closer 派生自一次随时可能被其他写入方作废的已存储读取。当两个 harness 进程共享同一存储根并打开同一会话——一个是活动会话，另一个执行冷历史加载或恢复——冷侧会把它基于快照计算出的合成中断轮次 closer 追加进日志，而活动所有者仍按自己的计数器继续为事件编号。两侧的追加都通过了校验，日志于是出现重叠的 seq 以及多余的种子 end-seed 标记，此后每次读取都会以 `corrupt session log: seq gap in committed region` 拒绝该产物，用户侧表现为历史加载失败，且除字节级手术外没有恢复路径。

## 决策

`JsonlSessionPersistence` 为每个会话维护一个持久化字节大小基线：在延迟实体化时设置，在每次 fsync 提交的 append 后推进，在修复截断时重置，并在每次修订稳定的采用读取（`readPrefix`）中建立。写入前，每次 append 都会比较文件当前大小与基线，对偏离即大声拒绝，错误中命名会话、两个大小以及并发写入原因。全新实例总是通过其采用读取获得基线，因此正常恢复不会误报。SQLite 对应实现已在逻辑上执行同一单写入方不变量（`append starts at seq X, stored next seq is Y`）；两个存储后端现在一致将外部增长视为大声拒绝，而不是静默交错。回归覆盖位于 `packages/session/session-persistence-jsonl/tests/jsonl.spec.ts`：在后端两次写入之间注入真实的外部追加，并附带一个全新实例的恢复对照组。

## 考虑过的替代方案

**按会话目录使用跨进程咨询锁。** 已拒绝：在 Windows 与 POSIX 上手工实现锁会带来陈旧持有者恢复和所有权生命周期问题，且持久化 seam 需要新的独占访问协议；大小校验用后端已有的原语即可发现冲突。

**把冷加载修复推迟到恢复发布时。** 现阶段已拒绝：平衡被中断的轮次是历史检查与 prepared-session 复用的正当工作，改变 `commitRepair` 的执行时机会把影响面扩大到本缺陷之外。有了追加时拒绝，并发活动所有者会让修复侧的下一次写入失败，而不是产生损坏。

**每次 append 前重新验证逻辑 seq。** 已拒绝：JSONL 是顺序介质，每次 append 都读取并解码压缩尾部会破坏流式设计；字节大小是该格式能提供的廉价持久化尾部代理。

**在协调器层执行该校验。** 已拒绝：物理布局属于各后端，SQLite 后端已在存储内验证；seam 层的游标校验仍然是自引用的内存状态，而非持久化事实。

## 后果

第二个进程打开活动会话后，其下一次持久化 append 会大声失败，而不是产出不可读的日志；失败一侧缓冲的事件按既有后台写入警告保留，文件字节与内存状态都不会被静默改写。残余缺口是实例首次接触一个从未读过或写过的会话——此时还没有基线——已存储会话的采用读取和自行物化的新日志已经覆盖了这一窗口。操作者看到拒绝后必须先裁决哪个写入方拥有该会话再重试；错误同时给出两个大小以直接支持该诊断。
